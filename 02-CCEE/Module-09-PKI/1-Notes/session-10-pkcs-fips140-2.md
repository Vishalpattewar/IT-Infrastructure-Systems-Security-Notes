## 1. Public Key Cryptography Standards (PKCS)

### 1.1 What is PKCS?

**PKCS (Public Key Cryptography Standards)** is a
family of standards that define the formats,
protocols, and procedures for using public key
cryptography in real-world applications.

PKCS standards solve the **interoperability problem**:
how do different applications, libraries, and
hardware devices from different vendors handle
cryptographic data in a consistent, compatible way?

```
Without PKCS:
  OpenSSL uses format A for private keys
  Windows uses format B for private keys
  Java uses format C for private keys
  → No interoperability — you cannot use a key
    generated by one tool in another

With PKCS:
  All tools follow PKCS#8 for private key format
  All tools follow PKCS#12 for cert + key export
  All tools follow PKCS#7 for signed messages
  → Full interoperability across platforms
```

> [!IMPORTANT]
> PKCS standards do NOT define new cryptographic
> algorithms — they define the **data formats
> and protocols** for using existing algorithms
> (RSA, AES, SHA, etc.) consistently.

---

### 1.2 PKCS Origin and Maintainer

| Property | Detail |
|----------|--------|
| **Developed by** | RSA Security (originally) |
| **Year** | Started 1991 |
| **Current maintainer** | IETF (for most PKCS standards, adopted as RFCs) |
| **Original purpose** | Establish standards for RSA-based public key cryptography |
| **Who uses them** | Every major cryptographic library, PKI system, and security product |

> [!NOTE]
> RSA Security (the company founded by Rivest,
> Shamir, and Adleman) published the original PKCS
> standards in 1991 — before formal standardization
> bodies had caught up with public key cryptography.
>
> Most PKCS standards have since been adopted and
> updated by IETF as RFC documents — making them
> proper internet standards. For example:
> - PKCS#1 → RFC 8017
> - PKCS#5 → RFC 8018
> - PKCS#7 → RFC 5652 (CMS)
> - PKCS#10 → RFC 2986
> - PKCS#12 → RFC 7292

### 1.4 PKCS#1 — RSA Cryptography Standard

**PKCS#1** defines the fundamental formats and
operations for RSA cryptography.

| Property | Detail |
|----------|--------|
| **Current version** | PKCS#1 v2.2 (RFC 8017, 2016) |
| **Defines** | RSA key format, RSA encryption, RSA signatures, padding schemes |
| **File extensions** | .pem, .der (PEM-encoded RSA keys) |
| **PEM header** | `-----BEGIN RSA PRIVATE KEY-----` (traditional) |

**What PKCS#1 specifies:**

**1. RSA Key Pair Format:**
```
RSAPrivateKey (PKCS#1 format):
  version         (0 = two-prime RSA)
  modulus         (n = p × q)
  publicExponent  (e, typically 65537)
  privateExponent (d)
  prime1          (p)
  prime2          (q)
  exponent1       (d mod (p-1))
  exponent2       (d mod (q-1))
  coefficient     (q⁻¹ mod p)

RSAPublicKey:
  modulus         (n)
  publicExponent  (e)
```

**2. Padding Schemes (critical for security):**

| Scheme | Version | Purpose | Security |
|--------|---------|---------|---------|
| **PKCS#1 v1.5** | v1.5 | Encryption + signatures | ⚠️ Encryption vulnerable to Bleichenbacher |
| **OAEP** | v2.0+ | Encryption only | ✅ Recommended for encryption |
| **PSS** | v2.1+ | Signatures only | ✅ Recommended for signatures |

> [!IMPORTANT]
> **For RSA encryption:** Use **OAEP** padding
> (Optimal Asymmetric Encryption Padding) —
> not PKCS#1 v1.5 (vulnerable to Bleichenbacher
> attack).
>
> **For RSA signatures:** Use **PSS** padding
> (Probabilistic Signature Scheme) —
> not PKCS#1 v1.5 (though still widely used
> for compatibility reasons).

---

### 1.5 PKCS#5 — Password-Based Cryptography

**PKCS#5** defines methods for deriving
cryptographic keys from passwords — making
password-based encryption practical and secure.

| Property | Detail |
|----------|--------|
| **Current version** | PKCS#5 v2.1 (RFC 8018, 2017) |
| **Key function** | Defines PBKDF1 and PBKDF2 |
| **Primary use** | Encrypting private keys with a password, file encryption, WPA2 |

**PBKDF1 vs PBKDF2:**

| Property | PBKDF1 | PBKDF2 |
|----------|--------|--------|
| **Status** | ❌ Legacy | ✅ Current standard |
| **Max key length** | 20 bytes (SHA-1) | Unlimited (depends on hash) |
| **Algorithm** | Hash-based (MD2, MD5, SHA-1) | HMAC-based (any hash) |
| **Iterations** | Variable | Variable (minimum 1000+ recommended) |
| **Defined in** | PKCS#5 | PKCS#5 (v2.0+) |

**PBKDF2 formula:**
```
DK = PBKDF2(PRF, Password, Salt, Iterations, dkLen)

Where:
  PRF        = Pseudo-Random Function (e.g., HMAC-SHA-256)
  Password   = User's password
  Salt       = Random salt (prevents rainbow tables)
  Iterations = Number of times PRF is applied
               (higher = slower = harder to brute force)
  dkLen      = Desired length of derived key

Example:
  DK = PBKDF2(HMAC-SHA-1, "password", "salt", 1000, 16)
  → 16-byte key derived after 1000 iterations
```

**Where PBKDF2 is used:**

| Application | Details |
|-------------|---------|
| **WPA2/WPA3** | Derives PMK (Pairwise Master Key) from Wi-Fi passphrase |
| **PKCS#8 encrypted private keys** | Protects private key files with a password |
| **PKCS#12** | Encrypts the certificate+key bundle |
| **iOS/Android encryption** | Device storage encryption derived from PIN/passphrase |
| **Django/Flask** | Web frameworks use PBKDF2 for password hashing |
| **LUKS (Linux disk encryption)** | Derives disk encryption key from passphrase |

> [!NOTE]
> PBKDF2 is NIST-approved (SP 800-132) and
> widely deployed — but it is not memory-hard,
> making it more vulnerable to GPU-based attacks
> than Argon2 or scrypt. For new password
> storage implementations, prefer Argon2id.

### 1.6 PKCS#7 — Cryptographic Message Syntax

**PKCS#7** (updated as **CMS — Cryptographic
Message Syntax** in RFC 5652) defines the format
for cryptographically protected messages —
messages that are signed, encrypted, or both.

| Property | Detail |
|----------|--------|
| **Current version** | CMS — RFC 5652 (supersedes RFC 2630) |
| **File extensions** | .p7b, .p7c, .p7m, .p7s |
| **Used in** | S/MIME email, code signing, certificate chains, PKCS#12 |

**PKCS#7 content types:**

| Content Type | Description | Use Case |
|-------------|-------------|---------|
| **Data** | Raw data (plaintext) | Encapsulated in other types |
| **SignedData** | Data + one or more digital signatures | S/MIME email signing, code signing |
| **EnvelopedData** | Encrypted data (for one or more recipients) | S/MIME email encryption |
| **SignedAndEnvelopedData** | Signed then encrypted | Email: signed + encrypted |
| **DigestedData** | Data + its hash (no signature) | Integrity only |
| **EncryptedData** | Encrypted data (no key info embedded) | Symmetric encryption |
| **AuthenticatedData** | Data + MAC (HMAC) | Authenticated integrity |

> [!NOTE]
> **PKCS#7 (.p7b) for certificate chains:**
> A .p7b file is commonly used to distribute a
> certificate chain (server cert + intermediate CA
> certs) without the private key. Windows uses
> .p7b for certificate imports.
>
> **PKCS#7 (.p7s) for S/MIME signatures:**
> Digitally signed emails use PKCS#7 SignedData
> format — the email body + digital signature
> bundled in a .p7s attachment.

### 1.7 PKCS#8 — Private Key Information Syntax

**PKCS#8** defines a standard format for storing
private keys — regardless of the algorithm
(RSA, ECDSA, DSA, etc.).

| Property | Detail |
|----------|--------|
| **RFC** | RFC 5958 (2010) |
| **Purpose** | Algorithm-independent private key format |
| **PEM header (unencrypted)** | `-----BEGIN PRIVATE KEY-----` |
| **PEM header (encrypted)** | `-----BEGIN ENCRYPTED PRIVATE KEY-----` |
| **Contrast with PKCS#1** | PKCS#1 is RSA-specific; PKCS#8 is algorithm-independent |

**Two formats:**

```
Unencrypted PKCS#8:
  PrivateKeyInfo:
    version (0)
    privateKeyAlgorithm (OID — RSA, EC, DSA etc.)
    privateKey (algorithm-specific key data)

Encrypted PKCS#8 (EncryptedPrivateKeyInfo):
  encryptionAlgorithm (PKCS#5 PBKDF2 + AES etc.)
  encryptedData (encrypted PrivateKeyInfo)
```

**Why PKCS#8 matters:**
- OpenSSL modern format uses PKCS#8 for all key
  types (`BEGIN PRIVATE KEY`)
- Older OpenSSL format used PKCS#1 for RSA
  (`BEGIN RSA PRIVATE KEY`) — algorithm-specific
- PKCS#8 is portable across algorithms —
  same format works for RSA, ECDSA, or any future
  algorithm

> [!TIP]
> **Quick identification:**
> - `-----BEGIN RSA PRIVATE KEY-----` → PKCS#1
>   (RSA-specific, traditional format)
> - `-----BEGIN PRIVATE KEY-----` → PKCS#8
>   (algorithm-independent, modern format)
> - `-----BEGIN ENCRYPTED PRIVATE KEY-----`
>   → PKCS#8 encrypted with a password
> - `-----BEGIN EC PRIVATE KEY-----` → EC-specific
>   (SEC 1 format — pre-PKCS#8 EC keys)

### 1.8 PKCS#10 — Certificate Signing Request

**PKCS#10** defines the format of a
Certificate Signing Request (CSR) — the document
an applicant sends to a CA to request a certificate.

| Property | Detail |
|----------|--------|
| **RFC** | RFC 2986 (2000) |
| **Purpose** | Standard format for CSR submission to CA |
| **PEM header** | `-----BEGIN CERTIFICATE REQUEST-----` |
| **File extensions** | .csr, .req |

**CSR Structure:**

```
CertificationRequest:
  │
  ├── CertificationRequestInfo (signed portion):
  │     ├── version (0)
  │     ├── subject (DN — Common Name, Org, Country etc.)
  │     ├── subjectPublicKeyInfo:
  │     │     ├── algorithm (RSA, EC, etc.)
  │     │     └── subjectPublicKey (the actual public key)
  │     └── attributes (optional — e.g., requested extensions)
  │
  ├── signatureAlgorithm (e.g., SHA256withRSA)
  │
  └── signature (applicant's signature over
                 CertificationRequestInfo using
                 corresponding private key)
```

**Why the CSR contains a self-signature:**
The applicant signs the CSR with their private key —
this is **Proof of Possession (PoP)** — it proves
to the CA that the applicant actually controls the
private key corresponding to the public key in the
CSR. Without this, anyone could submit someone
else's public key in a CSR.

**Creating a CSR with OpenSSL:**
```bash
# Generate private key
openssl genrsa -out server.key 2048

# Create CSR from private key
openssl req -new -key server.key -out server.csr

# Create CSR with specific subject (non-interactive)
openssl req -new -key server.key -out server.csr \
  -subj "/C=IN/ST=Maharashtra/L=Pune/O=DITISS/CN=www.ditiss.local"

# View CSR contents
openssl req -in server.csr -text -noout
```

### 1.9 PKCS#11 — Cryptographic Token Interface

**PKCS#11** (also called **Cryptoki** —
Cryptographic Token Interface) defines a
standard **API (Application Programming Interface)**
for interacting with cryptographic hardware tokens
such as HSMs, smart cards, and USB tokens.

| Property | Detail |
|----------|--------|
| **Full name** | Cryptoki (Cryptographic Token Interface) |
| **Latest version** | PKCS#11 v3.0 (2020) |
| **Maintained by** | OASIS (Organization for Advancement of Structured Information Standards) |
| **Purpose** | Standard API for applications to use hardware crypto tokens |

**What PKCS#11 enables:**
```
Application (OpenSSL, Firefox, Thunderbird)
         │
         │  PKCS#11 API calls
         ▼
PKCS#11 Driver/Library (vendor-provided)
         │
         │  Hardware-specific commands
         ▼
Hardware Token (HSM / Smart Card / USB Token)
         │
         → Private key operations happen INSIDE
           the hardware — key never leaves device
```

**PKCS#11 core concepts:**

| Concept | Description |
|---------|-------------|
| **Slot** | Physical slot for a token (e.g., smart card reader) |
| **Token** | The cryptographic device in the slot (smart card, HSM partition) |
| **Session** | A connection between the application and the token |
| **Object** | Data stored on the token (certificates, keys) |
| **Mechanism** | Cryptographic operation (e.g., RSA PKCS, AES CBC) |

**Where PKCS#11 is used:**

| Application | How |
|-------------|-----|
| **HSMs** | All major HSMs (nCipher, Thales, Utimaco) expose PKCS#11 API |
| **Smart cards** | SIM cards, bank cards, government ID cards |
| **USB tokens** | Aadhaar DSC tokens, India DSC dongles |
| **Firefox/NSS** | Firefox uses PKCS#11 modules to access smart card certs |
| **OpenSSL** | Can use PKCS#11 engine for HSM-backed operations |
| **Java (PKCS11 provider)** | Java Security Provider for PKCS#11 tokens |

> [!NOTE]
> The **PKCS#11 interface is the most important
> standard** for cryptographic hardware interoperability.
> Without it, every application would need custom
> drivers for every hardware token — making the
> ecosystem fragmented.

### 1.10 PKCS#12 — Personal Information Exchange

**PKCS#12** defines a file format that bundles
a **private key, certificate, and certificate chain**
into a single password-protected file.

| Property | Detail |
|----------|--------|
| **RFC** | RFC 7292 (2014) |
| **File extensions** | .pfx, .p12 |
| **Encoding** | Binary (can be Base64) |
| **Protection** | Password-based encryption (PKCS#5 PBKDF) |
| **Contents** | Private key + certificate + certificate chain |

**PKCS#12 structure:**
```
PKCS#12 file (.pfx / .p12):
  │
  ├── Certificate (end-entity)
  │
  ├── Certificate (Intermediate CA)  ← optional
  │
  ├── Certificate (Root CA)          ← optional
  │
  └── Private Key (encrypted with password)
```

**Common operations with PKCS#12:**

```bash
# Export certificate + private key to PKCS#12
openssl pkcs12 -export \
  -in certificate.pem \
  -inkey privatekey.pem \
  -certfile ca-chain.pem \
  -out bundle.pfx \
  -passout pass:MyPassword

# Import PKCS#12 — extract certificate
openssl pkcs12 -in bundle.pfx \
  -clcerts -nokeys \
  -out certificate.pem \
  -passin pass:MyPassword

# Import PKCS#12 — extract private key
openssl pkcs12 -in bundle.pfx \
  -nocerts -nodes \
  -out privatekey.pem \
  -passin pass:MyPassword
```

**When PKCS#12 is used:**

| Scenario | Usage |
|----------|-------|
| **Windows IIS/Exchange** | Import server certificate via .pfx file |
| **macOS Keychain** | Import certificates via .p12 files |
| **Java keystores** | Import into Java KeyStore |
| **Exporting from HSM** | Bundle cert + key for backup/migration |
| **Browser client certs** | Import personal cert into browser |
| **India DSC tokens** | DSC certificates provisioned as PKCS#12 |

> [!IMPORTANT]
> PKCS#12 files contain the **private key** —
> they MUST be password-protected.
> A .pfx or .p12 file without a strong password
> is a critical security risk — anyone who
> obtains the file can extract the private key.

## 2. FIPS 140-2

### 2.1 What is FIPS 140-2?

**FIPS 140-2 (Federal Information Processing
Standard Publication 140-2)** is a US government
standard for the **security requirements of
cryptographic modules** — the hardware and software
components that perform cryptographic operations.

| Property | Detail |
|----------|--------|
| **Full name** | FIPS PUB 140-2: Security Requirements for Cryptographic Modules |
| **Issued by** | NIST (National Institute of Standards and Technology) |
| **Published** | May 25, 2001 |
| **Supersedes** | FIPS 140-1 (1994) |
| **Superseded by** | FIPS 140-3 (2019) — transition ongoing |
| **Administrated by** | CMVP (Cryptographic Module Validation Program) — joint NIST + CCCS (Canada) |

> [!IMPORTANT]
> FIPS 140-2 is NOT about the cryptographic
> ALGORITHMS — it is about the cryptographic
> MODULE that runs those algorithms.
>
> Think of it this way:
> - **FIPS 197** = AES algorithm standard
>   (what algorithm to use)
> - **FIPS 140-2** = How the MODULE implementing
>   AES must be secured and validated
>   (how the algorithm must be implemented
>   and protected)

---

### 2.2 FIPS 140-2 Security Levels

FIPS 140-2 defines **four security levels** —
each adding more physical and logical security
requirements:

#### Security Level 1 — Basic
- Minimum security requirements for a cryptographic
  module
- Production-grade components
- No specific physical security mechanisms required
- Allows software-only implementations
- **Use:** Software encryption libraries (OpenSSL
  FIPS module), basic software implementations

#### Security Level 2 — Tamper-Evidence
- All Level 1 requirements PLUS:
- **Tamper-evidence** — seals or pick-resistant
  enclosures that show evidence of physical tamper
- **Role-based authentication** — operators must
  authenticate using role-based authentication
- **Use:** Software on general-purpose hardware
  with physical tamper seals

#### Security Level 3 — Tamper-Resistance
- All Level 2 requirements PLUS:
- **Physical tamper resistance** — module detects
  and responds to physical tampering attempts
  (zeroizes keys if tamper detected)
- **Identity-based authentication** — stronger than
  role-based (individual identity verified)
- **Protection of CSPs** — Critical Security
  Parameters zeroized on tamper detection
- Environmental failure protection
- **Use:** HSMs for CA private keys, payment HSMs

#### Security Level 4 — Highest Security
- All Level 3 requirements PLUS:
- **Complete physical protection** — envelope of
  protection covering the entire module
- **Environmental attacks** — protection against
  voltage and temperature fluctuations
- **Use:** Extremely high-security applications —
  root key storage, national defense, payment
  system core infrastructure

**Level Comparison Table:**

| Requirement | Level 1 | Level 2 | Level 3 | Level 4 |
|-------------|---------|---------|---------|---------|
| Basic security | ✅ | ✅ | ✅ | ✅ |
| Tamper-evidence | ❌ | ✅ | ✅ | ✅ |
| Tamper-resistance | ❌ | ❌ | ✅ | ✅ |
| Identity-based auth | ❌ | ❌ | ✅ | ✅ |
| Key zeroization on tamper | ❌ | ❌ | ✅ | ✅ |
| Environmental protection | ❌ | ❌ | ❌ | ✅ |
| Software-only allowed | ✅ | ✅ | ❌ | ❌ |

> [!IMPORTANT]
> **Level 3 is the industry standard for CA
> private key protection** — CA/Browser Forum
> Baseline Requirements reference FIPS 140-2
> Level 3 for Intermediate CA HSMs.
>
> **Level 4 is extremely rare** — found only in
> the most sensitive applications like central
> bank key management and classified government
> systems.

---

### 2.3 FIPS 140-2 Requirements

FIPS 140-2 evaluates cryptographic modules across
**11 requirement areas:**

| Area | Requirement |
|------|-------------|
| **1. Cryptographic Module Specification** | Define boundary, components, mode of operation |
| **2. Cryptographic Module Ports and Interfaces** | Control all interfaces — data in, data out, control, status, power |
| **3. Roles, Services and Authentication** | Define operator roles and required authentication |
| **4. Finite State Machine** | Define all operational states and transitions |
| **5. Physical Security** | Physical protection measures (depends on level) |
| **6. Operational Environment** | Operating system security requirements |
| **7. Cryptographic Key Management** | Key generation, storage, distribution, destruction |
| **8. Electromagnetic Interference/EMC** | Meets FCC/CE electromagnetic standards |
| **9. Self-Tests** | Power-on and conditional tests to verify correct operation |
| **10. Design Assurance** | Documentation, configuration management, delivery |
| **11. Mitigation of Other Attacks** | Protection against side-channel attacks (Level 3+) |

**Key Concepts:**

**Cryptographic Module Boundary:**
The physical or logical boundary that separates
the module from the outside world. Everything
inside the boundary is subject to FIPS 140-2
requirements.

**CSP (Critical Security Parameter):**
Security-related information (keys, PINs, passwords)
whose disclosure or modification could compromise
the module's security. Must be protected and
zeroized when required.

**Zeroization:**
Overwriting all CSPs (keys, passwords) with zeros
or random data before the module is decommissioned
or when tamper is detected — ensuring no sensitive
data can be recovered.

### 2.4 FIPS 140-2 vs FIPS 140-3

| Property | FIPS 140-2 | FIPS 140-3 |
|----------|-----------|-----------|
| **Published** | 2001 | 2019 |
| **Status** | Active (transition period) | Current standard |
| **Based on** | Unique NIST requirements | ISO/IEC 19790:2012 + ISO/IEC 24759 |
| **Security levels** | 4 levels | 4 levels (same structure) |
| **Algorithm requirements** | Based on NIST approved algorithms | Same + post-quantum awareness |

### 3.1 PKCS#1 Padding Schemes — v1.5 vs OAEP
vs PSS

> [!NOTE]

**PKCS#1 v1.5 (legacy):**
```
RSA Encryption with PKCS#1 v1.5:
  EM = 0x00 || 0x02 || PS || 0x00 || M
  Where:
    PS = random non-zero padding bytes (≥ 8 bytes)
    M  = message to encrypt

Vulnerability: Bleichenbacher attack (1998)
  → Oracle tells attacker if padding is valid
  → Through millions of queries, plaintext recoverable
  → Still widely used for compatibility — high risk
```

**OAEP (Optimal Asymmetric Encryption Padding):**
```
RSA Encryption with OAEP:
  Uses two hash functions (typically SHA-1 or SHA-256)
  and a mask generation function (MGF)
  Randomized — same plaintext → different ciphertext
  Provably secure under RSA assumption (CCA2-secure)
  → Recommended for all new RSA encryption
```

**PSS (Probabilistic Signature Scheme):**
```
RSA Signature with PSS:
  Uses hash + salt → randomized signatures
  Same message signed twice → different signatures
  Stronger security proof than PKCS#1 v1.5 signatures
  → Recommended for all new RSA signatures
```

> [!IMPORTANT]
> Memory hook:
> - **OAEP** = for **Encryption**
>   (O = Open = you're sending something)
> - **PSS** = for **Signatures**
>   (S = Sign)

### 3.2 PKCS#5 vs PKCS#12 — Common Confusion

> [!NOTE]

| Comparison | PKCS#5 | PKCS#12 |
|-----------|--------|---------|
| **What it is** | Password-based key derivation | File format for cert + key bundle |
| **Primary function** | Derive encryption key from password | Package private key + cert + chain |
| **Used in** | WPA2, encrypted private keys, disk encryption | Windows IIS, macOS, certificate migration |
| **Contains algorithm** | PBKDF1, PBKDF2 | Internally uses PKCS#5 for encryption |
| **File format** | Not a file format — it's a derivation function | .pfx, .p12 file |

**Relationship:**
PKCS#12 USES PKCS#5 internally — the private key
inside a .pfx file is encrypted using PBKDF2
(PKCS#5) before being stored in the PKCS#12
container. They work together, not in competition.

### 3.5 ASN.1 and DER — Foundation of PKCS Formats

> [!NOTE]
> All PKCS formats use **ASN.1 (Abstract Syntax
> Notation One)** to define data structures and
> **DER (Distinguished Encoding Rules)** to
> encode them as binary.

**ASN.1:**
- A notation for describing data structures
  independent of any programming language or hardware
- Defines types: INTEGER, SEQUENCE, BIT STRING,
  OCTET STRING, OID (Object Identifier), etc.
- Used by X.509 certificates, CRLs, CSRs, PKCS formats

**DER:**
- A specific encoding of ASN.1 data → binary bytes
- Canonical — only one valid encoding per value
- Used for signing and verifying (deterministic)

**PEM:**
- Base64-encoded DER with header/footer lines
- Human-readable form of DER data
- All `-----BEGIN ...-----` files are PEM-encoded DER

**Encoding chain:**
```
ASN.1 definition
     ↓ DER encoding
Binary bytes (.der, .cer files)
     ↓ Base64 encoding
Text string (.pem files with -----BEGIN-----header)
```

### 3.6 FIPS 140-2 Validated vs FIPS 140-2
Compliant

| Term | Meaning |

### 3.7 CMVP — Cryptographic Module Validation
Program

### 3.8 Approved Algorithms Under FIPS 140-2

> [!NOTE]

### 3.11 OpenSSL and PKCS

> [!NOTE]
> OpenSSL implements most PKCS standards —
> understanding the command-line tools helps
> solidify the concepts.

**Key OpenSSL PKCS operations:**

```bash
# PKCS#10 — Generate CSR
openssl req -new -key private.key -out request.csr

# PKCS#8 — Convert PKCS#1 RSA key to PKCS#8
openssl pkcs8 -topk8 -in rsa.key -out pkcs8.key -nocrypt

# PKCS#8 — Encrypt private key with PBKDF2 (PKCS#5)
openssl pkcs8 -topk8 -in rsa.key -out enc.key \
  -v2 aes-256-cbc -v2prf hmacWithSHA256

# PKCS#12 — Create .pfx bundle
openssl pkcs12 -export -in cert.pem \
  -inkey key.pem -out bundle.pfx

# PKCS#12 — Extract from .pfx
openssl pkcs12 -in bundle.pfx -out extracted.pem

# PKCS#7 — View .p7b certificate chain
openssl pkcs7 -in chain.p7b -print_certs -text

# View any certificate
openssl x509 -in cert.pem -text -noout
```
