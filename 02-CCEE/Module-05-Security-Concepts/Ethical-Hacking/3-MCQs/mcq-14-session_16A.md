### Q01

**Which CIA triad pillar is EXCLUSIVELY targeted by a Denial of Service attack?**

- A) Confidentiality — because DoS prevents users from reading data
- B) Integrity — because DoS corrupts data in transit
- C) ✅ Availability — because DoS makes systems and services unreachable to legitimate users
- D) Both Confidentiality and Availability — because DoS also exposes system information

**Explanation:**

- **A** is incorrect — DoS attacks do not expose or read data. Confidentiality attacks (sniffing, credential theft) target data exposure. A DoS simply prevents access — it does not reveal content.
- **B** is incorrect — Integrity attacks modify data in transit or at rest (e.g., MITM packet modification, database tampering). DoS does not alter data — it prevents access to it.
- **C** ✅ is correct — DoS attacks target **Availability** exclusively. The goal is to make a system, service, or network resource unavailable to its legitimate users — by exhausting bandwidth, connection state tables, CPU, memory, or application resources. The data remains intact and confidential — it simply cannot be reached.
- **D** is incorrect — DoS does not expose system information as part of its attack mechanism. While reconnaissance may precede a DoS attack, the DoS itself does not violate confidentiality.

### Q02

**What is the MOST precise technical distinction between a DoS attack and a DDoS attack?**

- A) DoS uses UDP; DDoS uses TCP — the protocol difference determines the classification
- B) DoS targets servers; DDoS targets network infrastructure like routers and switches
- C) DoS is always volumetric; DDoS is always application-layer
- D) ✅ DoS originates from a single source machine; DDoS originates simultaneously from multiple distributed sources — typically a botnet — making IP-based blocking ineffective

**Explanation:**

- **A** is incorrect — both DoS and DDoS can use any protocol (UDP, TCP, ICMP). The protocol used determines the attack type (UDP flood, SYN flood) — not whether it is DoS or DDoS.
- **B** is incorrect — both DoS and DDoS can target servers, network devices, or any networked resource. The target type does not distinguish them.
- **C** is incorrect — both DoS and DDoS include volumetric, protocol, and application-layer variants. The attack category (volumetric/protocol/application) is independent of whether it is DoS or DDoS.
- **D** ✅ is correct — DoS originates from a **single attacker machine** — blocking that one source IP stops the attack. DDoS originates from **thousands or millions of compromised machines (bots) simultaneously**. Each bot has a unique IP address — often distributed across dozens of countries — making IP-based blocking completely ineffective. The structural difference in source count is the defining distinction.

### Q03

**A UDP flood attack sends packets to random UDP ports on a target server. Beyond the incoming flood consuming bandwidth, what SECONDARY exhaustion mechanism makes UDP floods particularly effective?**

- A) The server's ARP cache fills completely — causing Layer 2 forwarding failure
- B) UDP packets force TCP session teardown — exhausting the connection state table
- C) ✅ The server sends ICMP Destination Unreachable replies for each port with no listener — doubling the bandwidth consumption with outbound ICMP traffic
- D) UDP flood packets trigger kernel panics by exploiting reassembly buffer overflows

**Explanation:**

- **A** is incorrect — ARP cache exhaustion is related to MAC flooding attacks at Layer 2. UDP floods operate at Layer 4 and do not directly impact ARP cache size.
- **B** is incorrect — UDP is a connectionless protocol. There is no TCP session state to tear down. UDP and TCP operate independently.
- **C** ✅ is correct — when UDP packets arrive on ports where no application is listening, the server's IP stack generates an ICMP Type 3 "Destination Unreachable" message for each one. This outbound ICMP traffic is generated by the server itself — consuming its own outbound bandwidth and CPU in addition to the incoming flood. The attacker generates one stream of UDP packets; the victim generates a corresponding stream of ICMP replies — creating a double exhaustion effect.
- **D** is incorrect — standard UDP flooding does not cause kernel panics. Ping of Death (oversized ICMP) exploits reassembly buffer overflow — but that is a different attack involving malformed fragmented packets, not random UDP flooding.

### Q04

**The Ping of Death attack exploits a vulnerability in which specific phase of IP packet processing?**

- A) IP header checksum validation — attacker forges an incorrect checksum causing verification failure
- B) IP TTL decrement — attacker sends packets with TTL=0 causing router CPU exhaustion
- C) IP routing table lookup — oversized packet forces recursive routing loop
- D) ✅ IP fragment reassembly — oversized ICMP payload split across fragments exceeds the 65,535-byte buffer limit on reassembly causing buffer overflow and system crash

**Explanation:**

- **A** is incorrect — checksum validation failures cause packet drops, not system crashes. Forged checksums are a normal occurrence handled gracefully by IP stacks.
- **B** is incorrect — TTL=0 causes routers to drop the packet and send ICMP Time Exceeded — it does not cause CPU exhaustion at the target.
- **C** is incorrect — packet size does not affect routing table lookups. Routing decisions are based on destination IP — not packet size.
- **D** ✅ is correct — the maximum valid IP packet size is 65,535 bytes. ICMP has an 8-byte header, leaving a maximum payload of 65,527 bytes. A Ping of Death sends an ICMP Echo Request with a payload exceeding this limit. The oversized packet is split into fragments that each appear valid during transit (individual fragments are within size limits). At the destination, the OS attempts to reassemble them — the combined size exceeds the reassembly buffer — causing a buffer overflow that crashes or reboots the target OS. Modern OSes are patched against this.

### Q05

**Which DoS attack sends a TCP SYN packet where both the source IP address AND destination IP address are identical — and both source and destination ports are the same — causing the target system to enter a processing loop?**

- A) Teardrop Attack
- B) Fraggle Attack
- C) SYN Flood Attack
- D) ✅ Land Attack

**Explanation:**

- **A** is incorrect — a Teardrop attack sends IP fragments with overlapping offset values. It exploits the IP fragment reassembly algorithm — not TCP header values.
- **B** is incorrect — a Fraggle attack is a UDP-based broadcast amplification attack (variant of Smurf). It uses forged source IPs pointing to the victim — but source and destination are different.
- **C** is incorrect — a SYN flood sends many SYN packets with SPOOFED source IPs — but the source and destination IPs are different. The attack fills the server's backlog queue.
- **D** ✅ is correct — the Land attack constructs a TCP SYN packet with the SAME IP address as both source and destination, and the SAME port as both source and destination. When the target receives this packet, it sends a SYN-ACK back to itself — which triggers another SYN-ACK — creating a processing loop that exhausts CPU resources. Affected older Windows, BSD, and Cisco IOS systems. The attack vector is IP spoofing: the attacker spoofs the victim's own IP as the source.

### Q06

**Which of the following CORRECTLY classifies Slowloris as a DoS attack type and explains why it evades most volumetric DDoS detection systems?**

- A) Slowloris is a protocol attack — it exploits TCP SYN backlog overflow — volumetric detectors miss it because it uses UDP
- B) Slowloris is a volume attack — it generates Tbps of traffic — volumetric detectors are misconfigured to ignore HTTP traffic
- C) ✅ Slowloris is an application-layer attack — it uses minimal bandwidth by holding connections open with slow partial HTTP headers — volumetric detectors look for high traffic rates and miss low-bandwidth, high-connection-count attacks
- D) Slowloris is a reflection attack — it reflects HTTP responses from innocent web servers at the victim — volumetric detectors cannot identify the reflection source

**Explanation:**

- **A** is incorrect — Slowloris does not exploit TCP SYN backlog. It sends complete TCP connections (three-way handshake succeeds) and then sends partial HTTP requests very slowly. The TCP layer is fully functional — the attack targets the web server's connection limit at the application layer.
- **B** is incorrect — Slowloris generates very LOW bandwidth intentionally. A few kilobits per second can exhaust an Apache web server's connection pool. High bandwidth is the opposite of Slowloris's mechanism.
- **C** ✅ is correct — Slowloris opens many HTTP connections and keeps them alive by sending one HTTP header line every few seconds — preventing server timeout without completing the request. The server holds each connection open waiting for the request to complete. The bandwidth consumed is negligible — a few KB/s. Volumetric DDoS detection triggers on traffic rate thresholds — Slowloris never crosses them. It exhausts the **application-layer connection limit**, not bandwidth. Apache is vulnerable (thread-per-connection model); Nginx is resistant (event-driven model).
- **D** is incorrect — Slowloris is not a reflection attack. It connects directly to the victim web server from the attacker's machine. There are no innocent third-party reflectors involved.

### Q07

**In a three-tier DDoS botnet architecture, what is the specific role of Tier 2 (C2 servers / handlers) and why does this tier increase the attacker's operational security?**

- A) Tier 2 machines are the bots that actually generate attack traffic — they are called handlers because they handle packet crafting
- B) Tier 2 machines are the victims — the C2 servers receive and log incoming attack traffic for the attacker's analysis
- C) ✅ Tier 2 are intermediate command-and-control servers that relay commands from the attacker to bots — they provide a layer of indirection so the attacker's real IP is never directly visible to bots or investigators
- D) Tier 2 machines are network amplifiers that boost the DDoS traffic volume before it reaches the target

**Explanation:**

- **A** is incorrect — the bots (zombies) are Tier 3 — they generate the actual attack traffic. Tier 2 servers relay commands but do not generate attack packets themselves.
- **B** is incorrect — victims are not part of the DDoS infrastructure tiers. The C2 servers receive commands FROM the attacker and relay them TO bots — not the other way around.
- **C** ✅ is correct — in the three-tier model: **Tier 1** is the attacker (bot herder), **Tier 2** is C2 infrastructure (handlers/servers), **Tier 3** is the bots. The Tier 2 layer provides critical operational security — the attacker communicates only with Tier 2 servers. Bots only communicate with Tier 2 servers. Law enforcement tracing bot traffic finds C2 servers (often on bulletproof hosting or compromised machines) — not the actual attacker. The attacker's IP is never directly exposed to the bots or the victim.
- **D** is incorrect — C2 servers relay control commands — they do not carry or amplify attack traffic. Attack traffic flows directly from bots (Tier 3) to the target — bypassing C2 servers entirely.

### Q08

**Which amplification protocol achieved the highest amplification factor ever recorded in a real-world DDoS attack, and what was the approximate amplification ratio?**

- A) DNS — approximately 70× — used in the 2013 Spamhaus attack at 300 Gbps
- B) NTP — approximately 556× — used via the MONLIST command against major ISPs
- C) SNMP — approximately 650× — used in attacks against financial institutions
- D) ✅ Memcached — approximately 51,000× — used in the February 2018 GitHub attack that peaked at 1.35 Tbps

**Explanation:**

- **A** is incorrect — DNS amplification achieves approximately 70× amplification. The 2013 Spamhaus attack did use DNS amplification at 300 Gbps — but DNS is not the highest amplification factor.
- **B** is incorrect — NTP MONLIST achieves approximately 556× amplification — significant but far below Memcached.
- **C** is incorrect — SNMP GetBulk achieves approximately 650× amplification — second highest among common protocols — but still far below Memcached's record.
- **D** ✅ is correct — **Memcached UDP amplification** achieves approximately **51,000×** amplification — the highest ever recorded. Memcached is an in-memory caching system designed for internal network use, never meant to be internet-exposed. Attackers discovered that internet-exposed Memcached servers on UDP port 11211 would respond to tiny requests with massive data dumps. The February 2018 GitHub attack used ~50,000 Memcached servers with GitHub's IP spoofed as source — peaking at 1.35 Tbps. Days later a 1.7 Tbps Memcached attack was recorded.

### Q09

**An attacker wants to execute a DNS amplification DDoS attack against a victim. Which TWO conditions are BOTH required for this attack to work?**

- A) The attacker must control the victim's DNS resolver AND have a botnet of at least 1,000 bots
- B) ✅ The attacker must be able to spoof the victim's IP as the source address AND open DNS resolvers must be accessible that return large responses to small queries
- C) The DNS server must be running an unpatched version AND the victim must be using the same ISP as the open resolver
- D) The attacker must perform ARP poisoning first AND the victim must be on the same subnet as the DNS resolver

**Explanation:**

- **A** is incorrect — the attacker does not need to control the victim's DNS resolver. The attack uses OPEN (publicly accessible) resolvers as unwitting amplifiers. A botnet is useful for scale but a single machine sending spoofed queries to many resolvers can also work.
- **B** ✅ is correct — both conditions are required: **(1) IP spoofing capability** — the attacker must forge the victim's IP as the source address in DNS queries so that resolver responses are directed to the victim, not the attacker. **(2) Open DNS resolvers** — publicly accessible DNS resolvers that accept recursive queries from any IP and return large responses (e.g., DNS ANY queries returning large TXT/MX/A record sets) are needed as amplifiers. Without spoofing, responses come to the attacker, not the victim. Without open resolvers, there is nothing to amplify through.
- **C** is incorrect — the DNS server does not need to be unpatched (amplification exploits normal DNS functionality, not a vulnerability). The ISP relationship between victim and resolver is irrelevant — amplification works across any internet topology.
- **D** is incorrect — ARP poisoning is a Layer 2 attack for local network interception. DNS amplification is an internet-scale attack requiring no local network access. The victim and resolver do not need to be on the same subnet.

### Q10

**The NTP MONLIST command is exploited in amplification DDoS attacks. What does MONLIST do and why was it disabled in modern NTP implementations?**

- A) MONLIST synchronizes time between all NTP peers simultaneously — creating a broadcast storm when exploited
- B) MONLIST queries the NTP server's routing table — returning a large BGP prefix list that amplifies traffic
- C) ✅ MONLIST returns a list of the last 600 clients that communicated with the NTP server — a large response to a tiny request — enabling ~556× amplification when attacker spoofs victim's IP as source
- D) MONLIST disables rate limiting on the NTP server — allowing the attacker to flood it with unrestricted queries

**Explanation:**

- **A** is incorrect — MONLIST is a monitoring/status command — it returns client history data. It does not perform time synchronization and does not create broadcast storms.
- **B** is incorrect — MONLIST has no relationship to routing tables or BGP. NTP servers handle time synchronization only.
- **C** ✅ is correct — the `MONLIST` (monitor list) command in older NTP implementations returns a list of the last **600 IP addresses** that sent queries to the NTP server. This is a large response to a tiny request (~8-byte query → potentially 48-byte records × 600 entries = ~2.9KB response = **~556× amplification**). An attacker sends MONLIST queries to thousands of NTP servers with the victim's IP spoofed as source — all servers send their large MONLIST responses to the victim. NTP v4.2.7+ disabled MONLIST by default. Mitigation: `restrict default nomonlist` in ntp.conf.
- **D** is incorrect — MONLIST does not modify rate limiting settings. It is purely a read-only status query that returns monitoring data.

### Q11

**A DDoS attack is described as "multi-vector." What does this specifically mean and why is it more difficult to mitigate than a single-vector DDoS?**

- A) Multi-vector means the attack targets multiple victim servers simultaneously — harder to protect all servers at once
- B) Multi-vector means the botnet uses multiple C2 server locations — harder to take down all C2 infrastructure
- C) Multi-vector means the attack uses multiple IP protocols simultaneously — requires filtering all protocols at the firewall
- D) ✅ Multi-vector means the attacker combines multiple attack types simultaneously — such as volumetric flooding plus application-layer attack — so that mitigating one attack type does not stop the assault

**Explanation:**

- **A** is incorrect — targeting multiple victims is a coordination strategy but does not define "multi-vector." Multi-vector refers to the attack methodology, not the number of targets.
- **B** is incorrect — multiple C2 locations describe botnet resilience and infrastructure redundancy — not the attack vector strategy against the victim.
- **C** is incorrect — while a multi-vector attack may use multiple protocols, the defining characteristic is combining different ATTACK TYPES (volumetric + protocol + application) — not simply using different IP protocols.
- **D** ✅ is correct — a multi-vector DDoS simultaneously deploys multiple attack categories: for example, a volumetric UDP flood consuming bandwidth + a SYN flood exhausting connection state + an HTTP flood exhausting web server threads — all at the same time. When defenders implement scrubbing for the volumetric component, the application-layer component continues. When they address the SYN flood, the HTTP flood remains. Each mitigation measure only addresses one vector — the attacker continuously exploits the others. This forces defenders to implement layered, simultaneous mitigation across all three DoS categories at the same time.

### Q12

**What makes the Mirai botnet historically significant in the context of DDoS evolution — and what was its primary infection vector?**

- A) Mirai was the first botnet to use P2P C2 architecture — it infected Windows PCs via phishing emails
- B) Mirai was the first botnet to use DNS amplification — it infected corporate servers via SQL injection
- C) Mirai was the first botnet to achieve 1 Tbps DDoS — it infected Linux servers via SSH brute force with unique passwords
- D) ✅ Mirai demonstrated that IoT devices could form massive botnets — it infected cameras, DVRs, and routers by trying 61 hardcoded default credential pairs via Telnet

**Explanation:**

- **A** is incorrect — Mirai did not introduce P2P C2. It used a centralized C2 model. It also did not primarily infect Windows PCs — it targeted embedded Linux-based IoT devices via Telnet.
- **B** is incorrect — DNS amplification predates Mirai by years (Spamhaus 2013). Mirai primarily used UDP and DNS query floods, not DNS amplification as its innovation.
- **C** is incorrect — while Mirai did help achieve ~1.2 Tbps against Dyn, it did not infect Linux servers via SSH with unique passwords. Its mechanism was Telnet brute force using 61 HARDCODED DEFAULT credential pairs — not unique passwords.
- **D** ✅ is correct — Mirai's significance was demonstrating the **IoT attack surface** at scale. It infected internet-connected cameras, DVRs, and home routers by scanning the entire IPv4 internet on port 23 (Telnet) and attempting 61 hardcoded default username/password combinations (admin/admin, root/root, etc.). IoT manufacturers shipped millions of devices with identical default credentials that consumers never changed. ~600,000 devices were infected — generating ~1.2 Tbps against Dyn DNS. The Mirai source code was publicly released — spawning dozens of variants.

### Q13

**Which botnet C2 architecture is the MOST resilient against law enforcement takedown operations, and why?**

- A) IRC-based C2 — because IRC traffic is encrypted by default, making server identification impossible
- B) HTTP-based C2 — because HTTP traffic blends perfectly with normal web browsing, preventing detection
- C) ✅ P2P-based C2 — because there is no central server to seize — commands propagate peer-to-peer between bots — taking down one node does not disrupt the botnet
- D) DNS-based C2 — because DGA generates new domains faster than registrars can suspend them

**Explanation:**

- **A** is incorrect — IRC-based C2 has a single IRC server — the most significant point of failure. Law enforcement regularly takes down IRC-based botnets by seizing the IRC server. IRC traffic is not encrypted by default.
- **B** is incorrect — while HTTP C2 does blend with normal traffic, it still relies on centralized C2 web servers. Seizing or sinkholing those servers disrupts the botnet. HTTP C2 is more resilient than IRC but less resilient than P2P.
- **C** ✅ is correct — P2P botnet C2 has **no central server**. Commands are propagated from bot to bot across the peer network — each bot knows only a subset of other bots. There is no single point of failure to seize. Law enforcement cannot disrupt a P2P botnet by taking down one server — they would need to simultaneously identify and disrupt a sufficient fraction of all infected nodes globally. Examples: Storm Worm, ZeroAccess, Waledac. This is the most resilient architecture.
- **D** is incorrect — DGA (Domain Generation Algorithm) is used with HTTP-based C2 to improve resilience by rotating C2 domains — but the underlying infrastructure still has centralized servers that can be targeted. DGA improves resilience of HTTP C2 but does not make it as resilient as P2P.

### Q14

**A security analyst observes that an endpoint makes a small outbound HTTP GET request to an external IP every 30 minutes with consistent timing — regardless of user activity. No user is using the system at those times. What behavior does this MOST likely indicate?**

- A) A legitimate software update check — most applications check for updates on a schedule
- B) A web browser cache refresh — browsers periodically verify cached content freshness
- C) ✅ Bot beaconing — a bot malware instance checking in with its C2 server at regular intervals to receive commands while remaining dormant between callbacks
- D) DNS TTL refresh — the DNS resolver refreshing cached records for frequently visited domains

**Explanation:**

- **A** is a valid alternative but does not fully account for the described characteristics. Legitimate update checks typically occur during user activity, use HTTPS to official vendor domains (not unrecognized IPs), and appear in application logs. Consistent 30-minute intervals to an unrecognized IP with no user logged in is more suspicious.
- **B** is incorrect — browser cache refreshes are triggered by user browsing activity. An inactive system with no logged-in user does not trigger browser cache validation.
- **C** ✅ is correct — **bot beaconing** is the signature behavior of malware checking into a C2 server. Bots maintain a dormant state between commands but periodically "phone home" to check for new instructions. The consistent timing (every 30 minutes), small packet size, occurrence regardless of user activity, and outbound connection to an external IP are all classic beaconing indicators. Security analysts look for **regular interval outbound connections** as a primary botnet detection technique. Variations in interval (jitter) are added by sophisticated bots to evade exact-interval detection.
- **D** is incorrect — DNS TTL refreshes happen transparently at the DNS resolver level and do not generate direct outbound HTTP GET requests from endpoints to external IPs. DNS queries go to the configured resolver, not the authoritative server directly.

### Q15

**What is DNS sinkholing in the context of botnet countermeasures, and what is its effect on infected bot machines?**

- A) DNS sinkholing blocks all DNS traffic from infected machines — causing them to lose internet access entirely
- B) DNS sinkholing redirects all DNS traffic through a monitoring server — capturing all user browsing data
- C) DNS sinkholing replaces the bot malware's DNS entries on infected machines with harmless local addresses
- D) ✅ DNS sinkholing redirects C2 domain resolution to a security researcher-controlled server — bots attempting to contact the C2 receive the sinkhole IP instead, neutralizing command delivery while revealing infected machine IPs

**Explanation:**

- **A** is incorrect — sinkholing does not block all DNS traffic or remove internet access. Only the specific C2 domain is redirected — other DNS resolution continues normally.
- **B** is incorrect — sinkholing specifically targets known malicious C2 domains — not all DNS traffic. It is a targeted intervention, not broad surveillance.
- **C** is incorrect — sinkholing operates at the DNS resolver level (or through ISP/registry intervention on the domain), not on the infected machine itself. No changes are made to the bot malware's files or the infected machine's configuration.
- **D** ✅ is correct — DNS sinkholing works by taking control of C2 domain resolution. Security researchers, ISPs, or law enforcement work with domain registrars to redirect C2 domains to a sinkhole server they control. When bots attempt to resolve the C2 domain, they receive the sinkhole IP. Bots connect to the sinkhole instead of the real C2 — no commands are received — the botnet is neutralized. Additionally, the sinkhole logs all connecting IPs — revealing the full list of infected machines globally, enabling victim notification and cleanup.

### Q16

**Beyond DDoS attacks, which of the following represents a LEGITIMATE commercial revenue stream that malicious botnet operators use to monetize their infrastructure?**

- A) Selling captured network packets to competing ISPs for routing optimization
- B) Renting botnet capacity to academic researchers for distributed computing projects
- C) ✅ Click fraud — using bots to generate fraudulent clicks on pay-per-click advertisements — earning revenue from advertising networks that pay per click
- D) Selling the list of infected machine MAC addresses to hardware manufacturers

**Explanation:**

- **A** is incorrect — selling captured packets to ISPs is not a recognized botnet monetization model. ISPs have their own traffic visibility through legitimate means.
- **B** is incorrect — while distributed computing projects exist (SETI@Home, Folding@Home), legitimate research projects use voluntary opt-in clients — not compromised machines. Using infected machines for unauthorized distributed computing is illegal regardless of the purpose.
- **C** ✅ is correct — **click fraud** is a major botnet revenue source. Advertising networks pay website owners (or fraudsters) for each click on displayed ads. Botnet operators instruct bots to visit specific web pages and click on advertisements — generating pay-per-click revenue. ZeroAccess botnet at its peak was estimated to generate $2.7 million per day through click fraud. The activity is difficult to detect because each click comes from a different real IP address (the bot) and appears to be a legitimate user.
- **D** is incorrect — MAC addresses are not commercially valuable information to hardware manufacturers. Selling MAC address lists is not a recognized botnet monetization model.

### Q17

**In a Smurf attack, which entity actually sends the flood of ICMP Echo Reply packets that overwhelms the victim?**

- A) The attacker sends ICMP Echo Replies directly to the victim using a botnet
- B) The victim's own network equipment generates the ICMP replies in response to the attacker's probing
- C) ✅ The hosts on the amplifier network — they each respond to the broadcast ICMP Echo Request with an ICMP Echo Reply directed at the victim's spoofed source IP
- D) The victim's ISP generates ICMP replies as part of its ICMP rate-limiting mechanism

**Explanation:**

- **A** is incorrect — in a Smurf attack, the attacker sends only ONE initial ICMP Echo Request per amplification cycle — directed at the broadcast address of the amplifier network. The attacker does NOT send ICMP replies. The attacker does not need a botnet for this attack (though scale is amplified without one).
- **B** is incorrect — the victim's own network equipment does not generate replies. The victim is purely a recipient of unsolicited ICMP Echo Replies it never requested.
- **C** ✅ is correct — the Smurf amplifier is a third-party network. The attacker sends an ICMP Echo Request to the broadcast address of the amplifier network — with the victim's IP spoofed as the source. Every host on the amplifier network receives this broadcast and follows the ICMP protocol by sending an ICMP Echo Reply to the "source" — which is the victim's IP. If 300 hosts are on the amplifier network, each one sends a reply to the victim — 300 packets from 300 innocent hosts flood the victim. The amplifier network is an unwitting participant.
- **D** is incorrect — ISPs do not generate ICMP replies on behalf of customers as part of rate limiting. Rate limiting drops excess traffic — it does not generate new traffic directed at the victim.

### Q18

**What is the PRIMARY Cisco IOS command that prevents a router from participating as a Smurf attack amplifier, and what specifically does it do?**

- A) `ip verify unicast source reachable-via rx` — enables reverse path forwarding to block spoofed source IPs
- B) `no ip proxy-arp` — disables ARP proxy to prevent the router from responding to ARP broadcasts
- C) `ip access-list extended BLOCK_SMURF deny icmp any any echo` — blocks all ICMP Echo Requests at the router
- D) ✅ `no ip directed-broadcast` — prevents the router from forwarding broadcast-addressed packets into the local subnet, eliminating the amplification mechanism

**Explanation:**

- **A** is incorrect — `ip verify unicast source reachable-via rx` implements unicast RPF (Reverse Path Forwarding) — a countermeasure against IP spoofing. While useful for preventing spoofed source IPs entering a network, it does not specifically prevent directed broadcast forwarding that enables Smurf amplification.
- **B** is incorrect — `no ip proxy-arp` disables the router from answering ARP requests on behalf of other hosts. This prevents certain ARP-based attacks but does not address directed broadcast forwarding — the Smurf amplification mechanism.
- **C** is incorrect — blocking ALL ICMP Echo Requests would break legitimate network diagnostics (ping). This is an overly broad measure. The specific vulnerability in Smurf is directed broadcast forwarding — not ICMP itself.
- **D** ✅ is correct — `no ip directed-broadcast` instructs the router NOT to forward packets destined for the subnet broadcast address (e.g., 192.168.1.255) into the local network. Without this forwarding, the attacker's ICMP Echo Request to the broadcast address never reaches the local hosts — they never send replies — the amplification does not occur. This has been the **default setting** in Cisco IOS since version 12.0 but must be explicitly configured on older equipment.

### Q19

**How does a Fraggle attack differ from a Smurf attack, and which TWO UDP ports are most commonly targeted?**

- A) Fraggle uses TCP instead of UDP; targets ports 80 and 443
- B) Fraggle targets the victim directly without broadcast amplification; uses UDP port 53 and 123
- C) Fraggle uses ICMP Echo Reply instead of Echo Request; targets ports 21 and 22
- D) ✅ Fraggle uses UDP instead of ICMP — same broadcast amplification concept — and targets UDP port 7 (echo service) and UDP port 19 (chargen service)

**Explanation:**

- **A** is incorrect — Fraggle specifically uses UDP, not TCP. TCP ports 80 and 443 are HTTP/HTTPS — irrelevant to Fraggle.
- **B** is incorrect — Fraggle DOES use broadcast amplification — that is its defining characteristic shared with Smurf. UDP ports 53 and 123 are DNS and NTP — not the primary Fraggle targets.
- **C** is incorrect — Fraggle does not use ICMP at all. Using ICMP Echo Reply instead of Echo Request would still be ICMP — not UDP. Ports 21 and 22 are FTP and SSH — not Fraggle targets.
- **D** ✅ is correct — Fraggle is identical in concept to Smurf (broadcast amplification with IP spoofing) but uses **UDP** instead of ICMP. The attacker sends UDP packets to the broadcast address with the victim's IP spoofed as source. The target ports are **UDP port 7** (echo service — any UDP data received is echoed back) and **UDP port 19** (chargen service — responds with a stream of characters). Both services amplify the traffic by responding to each broadcast. Fraggle is less effective today because UDP echo and chargen services are disabled by default on modern operating systems.

### Q20

**A Teardrop attack exploits which specific property of IP packet fragmentation?**

- A) IP fragments from the same packet have different source IP addresses — the reassembly algorithm crashes when trying to validate them
- B) IP fragments exceed the maximum TTL value — the reassembly timer overflows causing a kernel panic
- C) ✅ IP fragments with OVERLAPPING offset values are sent — when the target OS reassembly algorithm processes fragments where fragment 2 starts before fragment 1 ends, it crashes due to negative-length calculation or buffer confusion
- D) IP fragments are sent out of order with gaps between them — the OS waits indefinitely for missing fragments causing memory exhaustion

**Explanation:**

- **A** is incorrect — all fragments of the same IP packet share the same source IP address. The reassembly algorithm does not validate source IPs across fragments.
- **B** is incorrect — IP fragment TTL values are independent per fragment and do not relate to the reassembly timer or offset calculations. TTL overflow is not the mechanism.
- **C** ✅ is correct — IP fragmentation uses an **offset field** to indicate where each fragment's data belongs in the reassembled packet. Normal fragments: Fragment 1 offset=0 length=200 (bytes 0–199), Fragment 2 offset=200 (starts at byte 200). Teardrop sends: Fragment 1 offset=0 length=200 (bytes 0–199), Fragment 2 offset=80 (starts at byte 80 — **overlapping** with Fragment 1 by 120 bytes). The reassembly algorithm on vulnerable OSes attempts to calculate the data to copy from Fragment 2: `length - (F1_end - F2_start) = 200 - (199 - 80) = 200 - 119 = 81 bytes`. On vulnerable OSes, this calculation produces undefined behaviour (negative values or underflow) — causing kernel panic or system crash.
- **D** is incorrect — out-of-order fragments with gaps cause the OS to wait for missing fragments (controlled by a reassembly timer) — this causes memory holding for partial packets but not the specific crash mechanism of Teardrop. Teardrop requires overlapping offsets, not gaps.

### Q21

**Which of the following scenarios CORRECTLY describes the role of IP spoofing in a SYN flood attack and why it is essential to the attack's effectiveness?**

- A) IP spoofing is used to hide the attack traffic from firewalls — spoofed packets bypass stateful inspection rules
- B) IP spoofing allows the attacker to send packets faster than their real IP would permit — removing rate limiting restrictions
- C) ✅ IP spoofing prevents the server's SYN-ACK responses from reaching any real machine that would send RST packets — ensuring half-open connections remain in the backlog queue until timeout instead of being cleared
- D) IP spoofing is optional in SYN flooding — it is only used when the attacker wants to remain anonymous

**Explanation:**

- **A** is incorrect — stateful firewalls track connection state regardless of source IP. A spoofed source IP does not bypass stateful inspection — the firewall still sees the SYN packet and tracks it. IP spoofing's benefit in SYN flooding is specifically about RST prevention, not firewall bypass.
- **B** is incorrect — IP spoofing does not remove rate limiting on the attacker's side. The attacker's outbound bandwidth is still constrained by their connection. Rate limiting on the target side limits per-source-IP rates — but the attacker uses DIFFERENT random spoofed IPs for each packet, so each "source" appears to be within rate limits.
- **C** ✅ is correct — here is the precise mechanism: if the attacker uses their REAL IP, the server sends SYN-ACK to the attacker. The attacker's OS, having never initiated this connection, automatically sends a TCP RST — which tells the server to remove the half-open entry from the backlog. The backlog queue is self-cleaning. With SPOOFED IPs: the server sends SYN-ACK to random IPs that did not send the original SYN. Those machines send RST (if they exist) or nothing (if the IP is unused). But critically, the attacker's machine never sends RST — the half-open entries stay in the queue for the full SYN timeout period (up to 75 seconds) — the queue fills and stays full.
- **D** is incorrect — IP spoofing is NOT optional for an effective SYN flood against a patched server. Without spoofing, the attacker's own OS clears the half-open entries by sending RST responses. The backlog self-cleans and never fills. Anonymity is a secondary benefit — the primary technical necessity is preventing RST packets from clearing the half-open queue.

### Q22

**How do SYN Cookies prevent SYN flood attacks from exhausting the server's TCP connection backlog?**

- A) SYN Cookies block all SYN packets from unknown source IPs — only whitelisted clients can initiate connections
- B) SYN Cookies increase the backlog queue size dynamically — proportional to incoming SYN rate
- C) SYN Cookies use a firewall to complete the TCP handshake before forwarding connections to the server
- D) ✅ SYN Cookies encode connection state cryptographically into the SYN-ACK sequence number — the server allocates NO memory for half-open connections until the final ACK is received and the cookie is validated

**Explanation:**

- **A** is incorrect — SYN Cookies do not whitelist or block clients based on IP. They allow connections from ANY source — but defer memory allocation until the handshake completes. Unknown IPs are not blocked — they simply do not result in memory allocation until proven legitimate.
- **B** is incorrect — SYN Cookies do not dynamically expand the backlog queue. They eliminate the need for the backlog queue entirely for new connections — because no state is stored until the ACK arrives.
- **C** is incorrect — a firewall TCP SYN proxy is a separate, related countermeasure. SYN Cookies are implemented in the OS network stack itself — not in an external firewall completing the handshake.
- **D** ✅ is correct — with SYN Cookies: when a SYN arrives, the server computes a cryptographic hash of the 5-tuple (source IP, source port, destination IP, destination port, timestamp) — this becomes the initial sequence number in the SYN-ACK. **No TCB entry is allocated — no memory consumed.** When the legitimate client responds with ACK (acknowledging seq+1), the server recomputes the expected cookie and validates it. Only if the cookie is valid does the server allocate a TCB and establish the connection. Spoofed SYN packets never produce a valid ACK — no memory is ever allocated for them — the backlog cannot overflow.

### Q23

**Which Linux command enables SYN Cookies on a running system, and what does the value "1" signify?**

- A) `iptables -A INPUT -p tcp --syn -j SYNPROXY` — value 1 enables the iptables SYN proxy module
- B) `echo 1 > /proc/sys/net/ipv4/tcp_max_syn_backlog` — sets the backlog size to 1 entry
- C) ✅ `sysctl -w net.ipv4.tcp_syncookies=1` — enables SYN cookie generation; value 1 means SYN cookies are ACTIVE and will be used when the backlog is full
- D) `echo 1 > /proc/sys/net/ipv4/icmp_echo_ignore_broadcasts` — value 1 ignores broadcast ICMP to prevent Smurf

**Explanation:**

- **A** is incorrect — `iptables SYNPROXY` is a separate firewall-level SYN proxy mechanism — different from kernel-level SYN cookies. The command shown enables the iptables target, not the `tcp_syncookies` kernel parameter.
- **B** is incorrect — `tcp_max_syn_backlog` controls the maximum size of the half-open connection queue. Setting it to 1 would severely limit legitimate connections. This is a queue size parameter — not the SYN cookies toggle.
- **C** ✅ is correct — `sysctl -w net.ipv4.tcp_syncookies=1` enables SYN cookies in the Linux kernel. The value meanings are: `0` = disabled, `1` = enabled (SYN cookies used when backlog is full), `2` = always use SYN cookies regardless of backlog state. The `/proc` equivalent is `echo 1 > /proc/sys/net/ipv4/tcp_syncookies`. To make it permanent across reboots: add `net.ipv4.tcp_syncookies = 1` to `/etc/sysctl.conf`.
- **D** is incorrect — `icmp_echo_ignore_broadcasts` (value 1) makes the Linux kernel ignore ICMP Echo Requests sent to broadcast addresses — a Smurf amplification countermeasure. This is a completely different parameter from SYN cookies.

### Q24

**BCP38 is described as a critical countermeasure for multiple DoS attack types. What does BCP38 specify and which THREE attack types does it most directly prevent?**

- A) BCP38 specifies DNS validation — it prevents DNS amplification, DNS cache poisoning, and zone transfer abuse
- B) BCP38 specifies SSL certificate validation — it prevents SSL stripping, MITM, and session hijacking
- C) ✅ BCP38 specifies ISP ingress filtering — it prevents IP-spoofed attacks including Smurf attacks, SYN flooding with spoofed IPs, and DNS/NTP amplification attacks that require source IP spoofing
- D) BCP38 specifies botnet C2 domain blocking — it prevents botnet-driven DDoS, spam campaigns, and credential stuffing

**Explanation:**

- **A** is incorrect — BCP38 is about network ingress filtering, not DNS validation. DNSSEC and resolver configuration address DNS security.
- **B** is incorrect — BCP38 has nothing to do with SSL certificates or encrypted traffic inspection.
- **C** ✅ is correct — **BCP38** (Best Current Practice 38, RFC 2827) specifies that ISPs should configure their edge routers to drop packets arriving from customer connections where the **source IP does not belong to the customer's allocated address space**. This prevents IP spoofing at the source. All three attacks listed require IP spoofing: **Smurf** (victim's IP spoofed as source of broadcast), **SYN flooding** (random spoofed IPs prevent RST clearing), **amplification attacks** (victim's IP spoofed so amplifier responses hit victim). If BCP38 were universally deployed, these attacks would be impossible. However, adoption remains incomplete globally — particularly in developing country ISPs.
- **D** is incorrect — BCP38 does not address botnet C2 domains. Botnet C2 blocking is done through DNS sinkholing, BGP blackholing, and threat intelligence feeds — not ingress filtering of customer source IPs.

### Q25

**What is the key operational difference between BGP Blackholing (null routing) and DDoS scrubbing center mitigation from the victim's perspective?**

- A) BGP Blackholing is provided free by ISPs; scrubbing centers always require paid subscriptions
- B) BGP Blackholing mitigates application-layer attacks; scrubbing centers handle volumetric attacks only
- C) ✅ BGP Blackholing drops ALL traffic to the victim IP — stopping the attack but also blocking all legitimate users; scrubbing centers filter and remove only attack traffic — passing clean legitimate traffic to the victim
- D) BGP Blackholing works only for UDP attacks; scrubbing centers handle all protocol types

**Explanation:**

- **A** is incorrect — while some ISPs offer basic blackholing, payment models vary. Scrubbing centers also offer different tiers. Cost is not the defining operational distinction.
- **B** is incorrect — BGP Blackholing and scrubbing centers both primarily address volumetric attacks. Neither is exclusively limited to application-layer or volumetric attacks by definition.
- **C** ✅ is correct — this is the critical operational tradeoff: **BGP Blackholing** (null routing or RTBH) routes the victim IP to a null interface — all traffic (attack AND legitimate) is dropped. The attack stops — but so does legitimate service. The victim's service remains unavailable. **Scrubbing centers** (Akamai Prolexic, Cloudflare, Radware) receive all traffic for the victim, apply deep packet inspection and behavioral analysis to identify attack traffic, drop attack packets, and forward only clean legitimate traffic to the victim. Service remains available during a scrubbing-mitigated attack. Scrubbing is preferable but requires infrastructure and cost — blackholing is a blunt emergency measure.
- **D** is incorrect — BGP Blackholing and scrubbing centers are both protocol-agnostic. They operate at routing (BGP) or network/application (scrubbing) levels — not specific to UDP or any single protocol.

### Q26

**A server administrator notices the following output when checking the TCP connection state:**

    netstat -an | grep SYN_RCVD

    [hundreds of entries from different source IPs, all to port 443]

**What attack is occurring and what is the IMMEDIATE most effective host-level mitigation?**

- A) ARP poisoning — immediately enable Dynamic ARP Inspection on the connected switch
- B) MAC flooding — immediately configure port security on the switch port
- C) DNS cache poisoning — immediately enable DNSSEC validation on the resolver
- D) ✅ SYN flood attack — immediately verify SYN cookies are enabled with `sysctl net.ipv4.tcp_syncookies` and enable them if disabled

**Explanation:**

- **A** is incorrect — ARP poisoning does not produce hundreds of SYN_RCVD TCP connection states. ARP attacks affect Layer 2 forwarding — they do not create TCP half-open connections on the server.
- **B** is incorrect — MAC flooding affects switch CAM table behaviour. It does not create TCP SYN_RCVD entries on server connection state tables.
- **C** is incorrect — DNS cache poisoning affects DNS resolution — it does not produce TCP SYN_RCVD states on non-DNS servers (port 443 is HTTPS). DNS poisoning operates at the DNS protocol level.
- **D** ✅ is correct — **SYN_RCVD** is the TCP state where the server has sent SYN-ACK but not yet received the final ACK. Hundreds of SYN_RCVD entries from different source IPs to the same port is the textbook signature of a **SYN flood attack**. The server's backlog queue is being exhausted. The immediate host-level mitigation is ensuring **SYN cookies** are active: `sysctl net.ipv4.tcp_syncookies` (should return 1). If 0, enable immediately with `sysctl -w net.ipv4.tcp_syncookies=1`. SYN cookies eliminate the half-open backlog exhaustion without blocking legitimate clients.

**The GitHub DDoS attack of February 2018 peaked at 1.35 Tbps and was mitigated in approximately 20 minutes. Which attack method was used, what made it uniquely powerful, and which service mitigated it?**

- A) DNS amplification at 70× — powerful because DNS is universally open — mitigated by Cloudflare anycast
- B) NTP amplification at 556× — powerful because NTP MONLIST was still enabled — mitigated by GitHub's own IPS

### Q28

**Under Indian IT Act 2000, which specific section EXPLICITLY names "denial of service" as an offence — and what is the nature of liability under that section?**

- A) Section 66 — criminal liability — up to 3 years imprisonment for any DoS attack
- B) Section 66F — criminal liability — life imprisonment for DoS on any computer system
- C) Section 43(a) — civil liability — covers unauthorized access including DoS attacks
- D) ✅ Section 43(f) — civil liability — specifically names denial of service as causing damage by preventing legitimate access — compensation up to ₹1 crore

**Explanation:**

- **A** is incorrect — Section 66 covers criminal computer offences broadly (dishonest or fraudulent acts under Section 43) — it does not specifically name "denial of service" explicitly. It applies to DoS as criminal conduct but is not the section that explicitly names DoS.
- **B** is incorrect — Section 66F covers cyberterrorism — specifically attacks on critical infrastructure with intent to threaten national security. It imposes life imprisonment but is reserved for the most severe cases targeting critical infrastructure — not all DoS attacks.
- **C** is incorrect — Section 43(a) covers unauthorized ACCESS to a computer system — not specifically denial of service. Unauthorized access and denial of service are separate offences under different sub-sections.
- **D** ✅ is correct — **Section 43(f)** of the IT Act 2000 explicitly states that any person who knowingly or intentionally **"denies or causes the denial of access to any person authorized to access any computer, computer system or computer network"** shall be liable to pay damages by way of compensation not exceeding ₹1 crore. This is a **civil liability** provision — the victim can claim compensation. For **criminal prosecution**, Section 66 applies additionally. For attacks on critical infrastructure with national security intent, Section 66F (life imprisonment) is the applicable provision.
